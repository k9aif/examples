    How it fits together

    The OpenAI Agents SDK runs the agent loop. K9-AIF wraps it with an orchestrator adapter (OpenAIAgentsOrchestratorAdapter). The adapter is an orchestrator, so in a deployed K9-AIF application the Router sends it the event weather.lookup. This local example calls it directly. On this path the SDK's Runner and agent take the place of K9-AIF's Squad and Agent.

    Author's recommendation

    I don't let the model decide which agent runs next. In K9-AIF, each agent is an individual, runnable unit, and the squad invokes them in a known sequence set by the architecture. A squad stays small, at most five agents, and a synthesis step can combine their results at the end. The same input takes the same path every time, so the flow can be tested, audited and explained.

    The OpenAI Agents SDK supports this directly; its multi-agent guide calls it orchestrating via code, and K9-AIF does it with K9OpenAIAgent (k9-aif 1.28.0). This demo runs a single agent; the Multi-agent tab is an exercise that builds three OpenAI agents run this way, with a sample run of the result. Handoffs, where the model picks the specialist, stay available as an explicit opt-in, for open-ended conversations where that choice is the point.

    Ravi Natarajan, author of K9-AIF

    The classes

    The adapter is part of the K9-AIF framework (k9_aif_abb/k9_adapters/openai_agents/), the same shape as its CrewAI, LangGraph and Claude Agent SDK adapters: a facade, an orchestrator adapter that extends BaseOrchestrator and BaseAdapter, and a payload mapper. This example only configures it. Source: github.com/k9aif/k9-aif-framework · k9_adapters/openai_agents.

    What OpenAI's SDK gives, and what K9-AIF adds

    OpenAI Agents SDK: the agent loop, tools, handoffs, guardrails you attach per agent or tool, approvals, tracing, and any OpenAI-compatible model.

    Its agent guardrails check the first agent's input and the last agent's output. Its tool guardrails don't reach hosted tools or handoffs. Traces go to OpenAI by default.

    K9-AIF: one governance configuration for every agent runtime. Shield on every step of every agent, Zero Trust per caller and per agent, and the K9 Model Router choosing each model by eligibility first.

    The adapter builds every agent and tool itself, so hosted tools can't be added, and keeps SDK traces local unless told otherwise.

    Who decides which agent runs next?

    The OpenAI Agents SDK offers two ways. With handoffs, the model decides: each handoff is offered to the model as a tool (transfer_to_weather_agent), described by that agent's YAML description, and the model picks one. With orchestrating via code, as the SDK's multi-agent guide calls it, your code sets the order; in the guide's words, this "makes tasks more deterministic and predictable, in terms of speed, cost and performance." K9-AIF supports both, and governs both.

    K9-AIF squad (default)Handoffs (opt-in)
    Who picks the next agentThe squad's flowThe model, from the agents' descriptions
    Same input, same path?YesNot guaranteed
    FitsKnown steps: records, rules, approvalsOpen-ended, conversation-style requests
    In the design specAgent Routing: sequence (or nothing)Agent Routing: handoffs
    Studio generatesA squad of K9OpenAIAgent stepsA handoff group (K9OpenAIAgentsAdapter), capped per run, with Zero Trust on every agent turn

    The two approaches, as class diagrams

    Studio generates one of these from the design spec. They are laid out the same way, so the difference is easy to see.

    1. K9-AIF squad (default)

    The squad is a BaseSquad with a flow. Each agent extends K9OpenAIAgent and runs as one step; the "then" arrows are the flow's order. This exercise uses this approach.

    2. Handoffs (opt-in)

    With Agent Routing: handoffs, a runtime module returns K9OpenAIAgentsAdapter; FrontDeskAgent is the entry agent, and the model may hand off to WeatherAgent or AttireAdvisorAgent.

    ⇩ Download design_spec.md
    1. Open K9X Studio, go to Intake, and upload design_spec.md.
    2. Check that the Agent Framework card shows OpenAI Agents SDK, with agent routing sequence. The spec sets both.
    3. Generate the canvas (one orchestrator, one squad, three OpenAI agents), then Generate Scaffold.
    4. Put current_weather from this example in runtimes/tools.py, and in WeatherAgent's YAML set tools: [current_weather] and model: tools.
    5. Add current_weather to approved_tools in config/config.yaml.
    6. Set OLLAMA_BASE_URL in .env, pull a tool-calling model (K9_MODEL_TOOLS, default qwen2.5:7b), put your question in config/scenario.json, and run ./run.sh.

    Accounts payable: an OpenAI agent pays, the rules decide, a person approves

    Pick an invoice. An OpenAI agent reads it, the K9X Rules Engine (currently GoRules) decides, and a second OpenAI agent pays. When the rules say a person must approve, the OpenAI SDK's own needs_approval pause becomes a task in K9X HIL (hil.k9x.ai) over Kafka. Approve or reject it below: the decision comes back on Kafka, the Router resumes, and the same OpenAI run carries on. Payments are simulated.

      Architecture: how the pieces talk

      K9-AIF RouterK9EventRouter routes event_type: openai.ap.invoice to Kafka openai.ap.in (routing table in config.yaml).
      OrchestratorAPOrchestrator applies Zero Trust and runs the ap_invoice squad. It knows only the squad (K9-DEC-002).
      Step 1 · OpenAIInvoiceAgent (K9OpenAIAgent): reads vendor, invoice and amount as structured output. Governed by Shield like every agent.
      Step 2 · RulesAPRulesAgent (K9RulesAgent + GoRulesAdapter): looks up the facts in the records and asks the K9X Rules Engine. Decision: auto pay, needs approval, or reject.
      Step 3 · OpenAIPaymentAgent (K9OpenAIAgent) calls pay_invoice. Its needs_approval_when reads the rules step's decision, so the OpenAI SDK pauses the run only when the rules said so. Skipped on reject.
      PauseOpenAIHILAdapter (BaseHILAdapter) saves the SDK's run state in PausedRunStore (PostgreSQL schema openai) and raises RequiresHIL. The orchestrator hands it to BaseHILOrchestrator.
      Kafka (Redpanda)hil.requests.openai-ap-payments, on the same Redpanda as das.k9x.ai.
      K9X HILA task in OpenAI Demo Application → Invoice Approvals. A person approves or rejects (here, or at hil.k9x.ai).
      Kafka (Redpanda)hil.replies.openai-ap-payments carries the decision, keyed by correlation_id.
      ResumeThe Router's listen_for_hil_replies claims the pending flow once and re-routes it. The squad skips steps 1 and 2; PaymentAgent restores the same OpenAI run, approves or rejects the waiting call, and finishes.
