Orchestration patterns

How agents built with the OpenAI Agents SDK can be arranged, in OpenAI's own words: what each pattern is, a diagram of how control moves, a few lines of SDK code, and the demo on this site that shows it.

Sources: OpenAI, A practical guide to building agents (single agent, Manager, Decentralized), and the SDK's multi-agent documentation (orchestrating via code).

Pattern 1 · one agent

Single agent

From A practical guide to building agents, p. 13

"Single-agent systems, where a single model equipped with appropriate tools and instructions executes workflows in a loop."
from agents import Agent, Runner, function_tool

@function_tool
def current_weather(zip_code: str) -> str: ...

agent = Agent(name="Weather agent",
              instructions="Answer weather questions for a US ZIP code.",
              tools=[current_weather])
result = await Runner.run(agent, "Weather in 30301?")
Who decidesThe agent's model, turn by turn: call a tool, or answer.
When to useFirst, and for longer than you'd think. The guide: "maximize a single agent's capabilities first … often a single agent with tools is sufficient." Each new tool adds a capability without a second agent.
Who answers the userThe agent.

Pattern 2 · several agents · the model decides

Manager (agents as tools)

From A practical guide to building agents, pp. 16–19

"A central 'manager' agent coordinates multiple specialized agents via tool calls, each handling a specific task or domain." It is "ideal for workflows where you only want one agent to control workflow execution and have access to the user."
tool call to a specialistits answer, back to the manager
# from the guide (p. 18), shortened
manager_agent = Agent(
    name="manager_agent",
    instructions="You are a translation agent. You use the tools given to you to translate. "
                 "If asked for multiple translations, you call the relevant tools.",
    tools=[
        spanish_agent.as_tool(tool_name="translate_to_spanish",
                              tool_description="Translate the user's message to Spanish"),
        french_agent.as_tool(...),
        italian_agent.as_tool(...),
    ],
)
result = await Runner.run(manager_agent, "Translate 'hello' to Spanish, French and Italian for me!")
Who decidesThe manager's model. Each specialist is offered to it as a tool, described by its tool_description; it calls one, some or all.
What a specialist seesOnly the input the manager writes for it, not the conversation. Its answer comes back to the manager as the tool's result.
Who answers the userAlways the manager. Control never leaves it.

Pattern 3 · several agents · the model decides

Decentralized (handoffs)

From A practical guide to building agents, pp. 20–21

"Handoffs are a one way transfer that allow an agent to delegate to another agent. In the Agents SDK, a handoff is a type of tool, or function. If an agent calls a handoff function, we immediately start execution on that new agent that was handed off to while also transferring the latest conversation state."
handoff: control moves, one waythe new agent answers the user
# from the guide (p. 21), shortened
triage_agent = Agent(
    name="Triage Agent",
    instructions="You act as the first point of contact, assessing customer queries and "
                 "directing them promptly to the correct specialized agent.",
    handoffs=[technical_support_agent, sales_assistant_agent, order_management_agent],
)
result = await Runner.run(triage_agent, "Where is my order?")
Who decidesThe triage agent's model. Each handoff is offered to it as a tool (transfer_to_<agent>), described by that agent; it picks one.
What the new agent seesThe whole conversation. It takes over from there, and may hand off again.
Who answers the userThe agent the conversation ends with. Triage never sees the answer. The guide: "optimal when you don't need a single agent maintaining central control or synthesis."

Pattern 4 · several agents · your code decides

Orchestrating via code

From the SDK's multi-agent documentation

Your code, not a model, decides which agent runs next. In the documentation's words, this "makes tasks more deterministic and predictable, in terms of speed, cost and performance."
order set by your code
# each agent runs on its own; plain code chains them
facts = await Runner.run(invoice_agent, invoice_text)          # step 1
decision = check_rules(facts.final_output)                     # step 2: no model
if decision == "pay":
    await Runner.run(payment_agent, facts.final_output)        # step 3
Who decidesYour code. Each agent's model still chooses its own tool calls inside its step.
When to useKnown steps: records, rules, approvals. Also fits chaining one agent's output into the next, or running agents in parallel and combining the results.
Who answers the userYour code, after the last step.

When to split into several agents

From A practical guide to building agents, pp. 15–16. The guide recommends one agent first, and more agents when it fails to follow complicated instructions or keeps picking the wrong tools.

Complex logic"When prompts contain many conditional statements (multiple if-then-else branches), and prompt templates get difficult to scale, consider dividing each logical segment across separate agents."
Tool overload"The issue isn't solely the number of tools, but their similarity or overlap." Use several agents when clearer tool names, parameters and descriptions don't help.
