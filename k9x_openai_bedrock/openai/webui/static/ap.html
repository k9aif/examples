K9-AIF Framework, K9X Ecosystem and OpenAI Agents SDK in Collaboration

Accounts payable: OpenAI agents read and pay invoices, the K9X Rules Engine decides, and a person approves in K9X HIL.

Why accounts payable. Accounts payable sits where outside vendors, internal approvers and payment systems meet, so it is one of the riskiest ways into an enterprise: every invoice brings in bank details, personal data and instructions written by someone outside. This demo shows K9-AIF holding that line around OpenAI agents: K9X Shield (part of the K9-AIF framework) stops a bad invoice before the model reads it, the K9X Rules Engine decides what may be paid, and K9X HIL puts a person in front of the risky ones.

Accounts payable: an OpenAI agent pays, the rules decide, a person approves

Pick an invoice. An OpenAI agent reads it, the K9X Rules Engine (currently GoRules) decides, and a second OpenAI agent pays. When the rules say a person must approve, the OpenAI SDK's own needs_approval pause becomes a task in K9X HIL (hil.k9x.ai) over Kafka. Approve or reject it below: the decision comes back on Kafka, the Router resumes, and the same OpenAI run carries on. Payments are simulated.

Demo only. In a production application this pane is not here: approvers sign in to K9X HIL themselves, prompted by the queue's notifications and escalation rules, and decide there. It is embedded in this demo so you can play the approver.

This task came in to K9X HIL on Kafka (hil.requests.openai-ap-payments), under OpenAI Demo Application → Invoice Approvals. This pane reads and decides it through K9X HIL's REST API (the API key stays on this server). The invoice itself is a PDF in object storage (S3/MinIO): the task carries its s3:// link, and K9X HIL fetches it for the reviewer. The decision itself goes back on Kafka (hil.replies.openai-ap-payments). You can also decide it at hil.k9x.ai with the demo login.

    RuleWhenDecision

    AP-02Invoice already paid or submitted (duplicate)reject
    AP-03Amount over $100,000needs approval (manager)

    AP-08Everything elsepay automatically

    The model only reads the vendor, invoice number and amount. The facts the rules decide on (vendor status, a changed bank account, a PO match, a duplicate) come from the records, never from the model.

    How an invoice flows

    Architecture: how the pieces talk

    K9-AIF RouterK9EventRouter routes event_type: openai.ap.invoice to Kafka openai.ap.in (routing table in config.yaml).
    OrchestratorAPOrchestrator applies Zero Trust and runs the ap_invoice squad. It knows only the squad (K9-DEC-002).
    Step 1 · OpenAIInvoiceAgent (K9OpenAIAgent): reads vendor, invoice and amount as structured output. Governed by Shield like every agent.
    Step 2 · RulesAPRulesAgent (K9RulesAgent + GoRulesAdapter): looks up the facts in the records and asks the K9X Rules Engine. Decision: auto pay, needs approval, or reject.
    Step 3 · OpenAIPaymentAgent (K9OpenAIAgent) calls pay_invoice. Its needs_approval_when reads the rules step's decision, so the OpenAI SDK pauses the run only when the rules said so. Skipped on reject.
    PauseOpenAIHILAdapter (BaseHILAdapter) saves the SDK's run state in PausedRunStore (PostgreSQL schema openai) and raises RequiresHIL. The orchestrator hands it to BaseHILOrchestrator.
    Kafka (Redpanda)hil.requests.openai-ap-payments on the enterprise Redpanda (Kafka API, in a Podman container), shared by every K9X application, each on its own topics.
    K9X HILA task in OpenAI Demo Application → Invoice Approvals. A person approves or rejects (here, or at hil.k9x.ai).
    Kafka (Redpanda)hil.replies.openai-ap-payments carries the decision, keyed by correlation_id.
    ResumeThe Router's listen_for_hil_replies claims the pending flow once and re-routes it. The squad skips steps 1 and 2; PaymentAgent restores the same OpenAI run, approves or rejects the waiting call, and finishes.
