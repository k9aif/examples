OpenAI guardrails · K9-AIF

Guardrails and Zero Trust

The OpenAI Agents SDK has guardrails, and OpenAI's guide explains how to layer them. This page takes the guide item by item and shows what K9-AIF puts in each place, and what is switched on in the demos on this site.

Source: OpenAI, A practical guide to building agents, pp. 24–31 (guardrails, human intervention).

What the guide says

Guardrails are one layer, by OpenAI's own account

"Guardrails are a critical component of any LLM-based deployment, but should be coupled with robust authentication and authorization protocols, strict access controls, and standard software security measures." p. 24
"Think of guardrails as a layered defense mechanism. While a single one is unlikely to provide sufficient protection, using multiple, specialized guardrails together creates more resilient agents." p. 25

So the question isn't guardrails or K9-AIF. K9-AIF uses the SDK's own guardrail hooks, fills them with ready-made checks, and adds the authorization and review that the guide says guardrails need beside them.

What protects you

The second line is the one that matters

Strip the "ignore all previous instructions" and the refund request is ordinary. Screening the words can't decide it. What decides it is the action: is it the customer's own account, and is the amount over the limit that needs a person? The guide names this case itself: "authorizing large refunds" is its example of a high-risk action that "should trigger human oversight" (p. 31).

The accounts payable demo is this case, live. An OpenAI agent prepares the payment, the K9X Rules Engine decides, and a payment over $15,000 pauses the OpenAI run for a person in K9X HIL, with role, deadline and audit trail. After the decision, the same run continues.

Zero Trust

What Zero Trust does, and how it differs from Shield

Shield and Guardian judge content: is this text an attack, harmful, leaking data? Zero Trust judges the caller: who is this, and may they reach this action or this agent? The two don't overlap.

Who is callingIdentity comes from the sign-in, not from what the request claims. In signed mode, only a signed identity stamp counts; a self-declared roles: ["admin"] is ignored.
May they reach itA role policy per action, and per agent: openai_agent:RefundAgent can be limited to staff, so a customer's run is refused when it reaches that agent, even after a handoff.
How risky is itRisk scoring and data-loss checks on the request, with sensitive fields masked before an agent sees them.

In these demos the role is chosen on the page (customer, staff, guest) so you can watch Zero Trust refuse a guest. A real deployment takes the role from sign-in.

In fairness

Where the SDK's guardrails are enough, and how the two fit

K9-AIF is built on themThe adapter attaches its checks through the SDK's own tool_input_guardrail and tool_output_guardrail, and its run hooks. It fills the SDK's mechanism; it doesn't replace it.
Where the SDK alone is enoughOne team, OpenAI only, low-risk actions, and the time to write and maintain the checks. Then the guide's advice and the SDK's guardrails will do.
Where K9-AIF adds mostMany agents (the SDK's agent-level guardrails see only the first agent's input and the last agent's output), checks before the run instead of beside it, authorization per agent, reviewed high-risk actions, and one configuration for every runtime: OpenAI, CrewAI, LangGraph, Claude Agent SDK.
